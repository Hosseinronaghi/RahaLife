# محدوده بررسی امنیت و پذیرش dev.3

این بررسی تضمین نبود همه باگ‌ها یا کد مخرب در کل زنجیره تأمین نیست و تأیید Google Play/App Store محسوب نمی‌شود.

## اصلاحات انجام‌شده
- صف قبلی شبکه‌ها در SharedPreferences متن آشکار داشت. اکنون AES-GCM با کلید تصادفی در Secure Storage و داده احرازاصالت‌شده ذخیره می‌شود.
- مهاجرت صف قدیمی ابتدا نسخه رمزگذاری‌شده را ثبت و سپس متن قبلی را حذف می‌کند. خرابی ciphertext یا نبود کلید باعث توقف امن می‌شود؛ صف خالی جایگزین داده خراب نمی‌شود.
- مشاهده/حذف/ارسال صف به شبکه + سرور + شناسه حساب محدود شد. افزودن هم‌زمان پیام‌ها، صف حساب دیگر را بازنویسی نمی‌کند.
- حذف محلی حساب نیازمند تأیید است و پیام‌های ارسال‌نشده همان حساب را پاک می‌کند. نشست سمت سرور با این کار لغو نمی‌شود.
- صف وابسته به دستگاه از export و restore بکاپ مستثناست تا ciphertext بدون کلید روی دستگاه دیگر وارد نشود.
- OAuth توکن‌ها را به endpoint ثابت HTTPS می‌فرستد، redirect HTTP توکن دنبال نمی‌شود، خطای Dio حاوی بدنه اعتبارنامه به UI منتقل نمی‌شود.
- هنگام ثبت و ارسال پشتیبان، فایل قبلی overwrite نمی‌شود؛ دانلود ناقص و فایل بیش از حد رد می‌شوند.
- callback وب کد ورود را در localStorage نمی‌نویسد؛ مقصد postMessage همان origin برنامه است.

## محدودیت‌های پابرجا و دروازه انتشار
- رمزگذاری صف محلی با E2EE پیام‌رسان متفاوت است. Matrix فعلی همچنان REST preview است؛ ارسال متن به اتاق رمزگذاری‌شده مسدود می‌ماند.
- Matrix SDK جدید به sqlite3 نسل ۳ نیاز دارد؛ پروژه و assets وب هنوز نسل ۲ هستند. ادغام SDK و vodozemac، migration و آزمون کلیدها انجام نشده‌اند. مجوز وابستگی SDK نیز باید در انتخاب نهایی لحاظ شود.
- XMPP صرفاً در دامنه توسعه ثبت شده؛ کلاینت و OMEMO پیاده نشده‌اند. حساب یا دکمه غیرعملی برای آن به کاربر نشان داده نمی‌شود. Matrix↔XMPP پل خودکار نیست.
- PHP Sync هنوز E2EE ندارد؛ اپراتور سرور می‌تواند داده همگام‌شده را بخواند. اشتراک حساس چرخه تا تکمیل رمزنگاری/مجوز/انقضا پذیرش نهایی ندارد.
- Google Drive، OneDrive، iCloud و Sync افزایشی ابرها هنوز تکمیل نیستند.
- امنیت Web به origin، HTTPS و نبود XSS وابسته است؛ Secure Storage مرورگر معادل سخت‌افزار امن موبایل نیست.
- بررسی جدید وابستگی ورود، ساخت native همه پلتفرم‌ها، تست امضای ارتقا، background، لغو دسترسی و پذیرش فروشگاهی هنوز لازم است.
- سرور MySQL واقعی و سناریوهای چند دستگاه اجرا نشده‌اند؛ تست‌های قبلی PHP در validation تاریخی‌اند و در این مرحله تغییر سرور داده نشده است.
- گزارش و فهرست گسترده کارهای باز در docs/v010/SCOPE_FA.md و گزارش dev.2 حفظ شده‌اند؛ این مرحله بستن همه درخواست‌ها نیست.

## سناریوهای پذیرش پس از ثبت اپ
۱. ورود/لغو ورود/عدم دسترسی، تغییر حساب و برگشت صحیح در هر پلتفرم.
۲. بکاپ همراه پیوست روی دستگاه اول؛ واردکردن کلید بازیابی و بازیابی در نصب تازه دستگاه دوم.
۳. انقضای access token، تازه‌سازی، لغو مجوز از Dropbox و تلاش مجدد؛ بدون نمایش وضعیت موفق کاذب.
۴. دو حساب پیام‌رسان با سرور یکسان، صف‌های مستقل، حذف یک حساب و باقی‌ماندن حساب دیگر.
۵. ارتقا از APK واقعی قبلی با همان applicationId و گواهی و versionCode بزرگ‌تر؛ داده و کلیدها باقی بمانند.
۶. بررسی privacy disclosure، حذف حساب/داده، مجوزهای ضبط، گزارش محتوای پیام و رفتار اعلان در گوشی واقعی.
